# Orbit native migration

This is an active migration, not a completed replacement. At the owner's explicit wrap-up request on 15 September, the native phone candidate was installed over the existing Orbit using the original signing key and the same application ID. Installation is not runtime, data-migration, physical performance or final design acceptance. Do not install another Orbit clone. The current stopping point and all deferred gates are in [WRAPUP-2026-09-15.md](WRAPUP-2026-09-15.md).

The [research addendum checklist](RESEARCH-ADDENDUM-CHECKLIST.md) reconciles all 13 additional requirements from 15 September against current implementation. It extends this goal and preserves completed work and approved design. Its unchecked requirements and the original acceptance gates below both remain binding; later chronological checkpoints supersede older implementation-status descriptions.

## Architecture audit — 14 September 2026

- Existing `android/src/com/mani/orbit` owns Samsung merged live steps, SQLite originals, validated workout persistence, monotonic elapsed time, countdown, GPS filtering, notifications and music session access. The native phone now uses `NativeSamsungHealth` / `SamsungDataImport` / `SamsungRecordCodec` for direct Samsung SDK history. The legacy Health Connect reader remains only in the old web project and is excluded from the native build along with the WebView entry point, browser feedback adapter and old permission activity.
- Existing `HealthRecordStore` deliberately accepts only Samsung-origin imports. Watch-origin records must not be inserted into that staging table or overwritten by an import. Extend storage with a source-aware durable receipt/outbox boundary before merging display projections.
- Existing health refresh is activity-owned and foreground-only. A native lifecycle adapter is the first step; background import requires separately granted platform access and WorkManager, not a hidden activity.
- The older `C:/HA/HEALTH APP` has a versioned protocol, bounded channel transfer, durable receipts before ACK, watch outbox retry and a coalescing dispatcher. It is read-only reference material. Reuse these proven invariants and relevant domain code; do not copy its full module graph or UI.
- Compose is already installed locally. Use native Compose on Android and Wear Compose on the watch. No HTML, WebView, JavaScript evaluation or bundled web assets in the new UI.

## Official research read in full

- [Design and build apps for watchOS 10](https://developer.apple.com/videos/play/wwdc2023/10138/): relevant detail first, brief focused interactions, predictable shallow navigation, shape-aware layouts, readable hierarchy, contextual colour. Orbit adaptation: live session first, a few focused watch pages, round-screen safe insets, meaningful motion and Android rotary/touch support. Do not duplicate watchOS APIs or rectangular Apple layouts.
- [Design widgets for the Smart Stack on Apple Watch](https://developer.apple.com/videos/play/wwdc2023/10309/): glanceability, consistent type/layout, recognisable context, timely relevance, useful entry points rather than duplicate session controls. Apply to Wear Tiles and complications; Android's ongoing activity owns quick return to a workout.
- [Build a multi-device workout app](https://developer.apple.com/videos/play/wwdc2023/10023/): one primary session with mirrored controls/state, live metrics during activity, richer post-workout analysis and stable identifiers/versions. Android needs its own durable Data Layer protocol; HealthKit mirroring is not available here.

Also read in full: [Design Live Activities for Apple Watch](https://developer.apple.com/videos/play/wwdc2024/10098/) and [What's new in watchOS 26](https://developer.apple.com/videos/play/wwdc2025/334/). Keep critical live state glanceable, minimise competing controls, preserve native interaction hierarchy and distinguish ongoing activity from all-day context. Use Wear equivalents, not Apple APIs. More specialised complication/workout UI research remains before final watch UI qualification.

## Platform sources checked

- [Health Services exercise architecture](https://developer.android.com/health-and-fitness/health-services/active-data): ExerciseClient and a foreground service own active tracking beyond the screen lifecycle; respect ambient batching.
- [MeasureClient](https://developer.android.com/health-and-fitness/health-services/active-data/measure-client): short foreground measurements, not the workout engine.
- [Wear Data Layer](https://developer.android.com/training/wearables/data/overview): matching application ID and signing identity; encrypted transport can route via Google when Bluetooth is unavailable.
- [Health Connect reads](https://developer.android.com/health-and-fitness/health-connect/read-data): background reading needs its own access grant. Samsung remains the authoritative imported history; watch collection must not double-count Samsung's merged totals.

- [Health Services permissions](https://developer.android.com/health-and-fitness/health-services/permissions): API 36+ uses granular heart/background health access, while older watches need the version-appropriate body-sensor permissions. Activity metrics use activity recognition; GPS needs location access.
- [Samsung Sensor SDK overview](https://developer.samsung.com/health/sensor/overview.html): v1.4.1 provides continuous HR/IBI, raw signals and supported on-demand measurements; per-device capability checks remain essential. It cannot be qualified in an emulator. Samsung sleep-stage history comes from the existing Samsung-origin import, not an invented on-watch staging algorithm.
- [Data Layer event handling](https://developer.android.com/training/wearables/data/events): listener service callbacks run on a background thread and can receive while the UI is absent. The phone receiver checks watch capability, commits the batch, then sends its hash-matched ACK.

The [Samsung Sensor SDK distribution process](https://developer.samsung.com/health/sensor/process.html) and [application verification](https://developer.samsung.com/health/sensor/guide/app-verification.html) were checked. Production access requires registered package/signature approval; developer mode is a testing path. Samsung-specific qualification remains pending and must not be represented as generic Health Services support.
